## Critical

### C1 — Detection loop never stops; orphan loop keeps counting reps after pause/unmount

**File:** `app/session/page.tsx:426` (guard), `:434` (await), `:564` (reschedule), `:571-575` (cleanup)
**Severity:** Critical

`detectAndAnalyze` guards on `sessionState !== 'active'`, but `sessionState` is captured in the
effect closure that only runs *when it is* `'active'` — so the check can never be true. The
function is async: the effect cleanup (`cancelAnimationFrame`, :572) runs while
`await detect(...)` (:434) is still pending, then the resumed continuation schedules a fresh
`requestAnimationFrame` at :564. That loop is tracked by nothing and never terminates.

Consequences:

- Reps are counted while the Paused overlay is on screen.
- `goodPostureTimeRef` / `totalActiveTimeRef` keep accumulating, skewing `form_quality_score`
  — which is the level-unlock gate (`lib/levels.ts:56`).
- Resume starts a **second** loop alongside the orphan, so reps double-count.
- Navigating away leaves inference running and setState firing on an unmounted tree.
- `completeSession()` can fire twice → duplicate `rep_data` rows.

**Suggested fix:** add an effect-scoped `let running = true`, set it `false` in cleanup, and
check it both at the top of `detectAndAnalyze` **and** immediately after every `await` before
scheduling the next frame. This is exactly the pattern the editor's test loop already uses
(`app/admin/exercises/[id]/edit/page.tsx:187,215`).

### C2 — Admin email and plaintext password committed to the repository

**File:** `supabase/scripts/set-admin.sql:1-3`; related `supabase/migrations/20260704000000_data_fixes.sql:269-271`
**Severity:** Critical

> **Security warning:** line 3 records the admin account's password (redacted here) in a tracked
> file, and the migration grants `is_admin = TRUE` to that same hardcoded address. Anyone with
> repository read access holds therapist-level credentials. Re-running the migration also
> re-grants admin to whoever controls that address at that time.

**Suggested fix:** rotate that account's password immediately; delete the password comment;
parameterize the email (a psql variable such as `:'email'`) instead of hardcoding it; and
remove the hardcoded admin grant from the migration.

### C3 — `therapy_sessions.stars_awarded` is client-writable, so the award-once dedup is bypassable

**File:** `supabase/migrations/20260718120000_star_integrity.sql:780` (column), `:806-811` (claim), `:865` (revoke); policy from `supabase/migrations/20260703000000_initial_schema.sql:60-62`
**Severity:** Critical

> **Security warning:** the migration revokes `update (total_stars)` on `profiles` but revokes
> nothing on `therapy_sessions`, and the policy "Users can update own sessions" permits a
> full-row update of your own rows. From the browser console:
> `update({ stars_awarded: false })` on an already-awarded session, then
> `rpc('award_stars', { p_session_id })` → +1 star, repeatable without limit.
>
> Same class of hole: a client can `insert` sessions and set `completed_at` and
> `form_quality_score = 100` itself, minting completed sessions and unlocking every level
> (`lib/levels.ts:56`). The invariant the migration header states — "server-owned",
> "awarded exactly once" — does not hold.

**Suggested fix:** revoke `update` on `(stars_awarded, completed_at, form_quality_score,
completed_reps, duration_seconds, user_id)` from `authenticated`, and move session completion
behind a `SECURITY DEFINER` RPC that stamps those columns server-side.

## Major

### M1 — Keypoint pixel space differs across recording / session / upload; every pixel threshold is miscalibrated

**Files:** `app/admin/exercises/new/page.tsx:88`, `app/session/page.tsx:314`,
`lib/detectionCore.ts:216,339`, `lib/poseDetection.ts:426,645,1045`
**Severity:** Major

The recorder requests 640×480; the patient session requests 1280×720; `detectionCore` scales
normalized landmarks by the *source* frame size. So stored keypoints and live keypoints live in
different coordinate spaces, and every pixel-valued threshold drifts:

- `levelingRules.maxDifference` (default 10 px, checked at `lib/poseDetection.ts:426`) is
  authored against 640×480 and validated against 720p → roughly 2× stricter in a real session.
- `MOVING_DISPLACEMENT_PX` and `TRIM_ENERGY_PX` (`lib/poseDetection.ts:645,1045` — the comment
  states "camera is 640×480") behave differently for a 1080p uploaded clip, producing a
  different trim and a different "moving joint" set, hence different derived criteria.

**Suggested fix:** normalize keypoints to one canonical space (fractions of frame width, or a
fixed 640×480) before storing and before validating; or store the source frame size with each
recording and rescale on read. Angles are scale-invariant, so only the pixel metrics need this.

### M2 — Editor skeleton canvas is hardcoded to 640×480, so uploaded-video demos draw off-screen

**File:** `app/admin/exercises/[id]/edit/page.tsx:397-405`
**Severity:** Major

`canvas.width = 640; canvas.height = 480; const scaleX = canvas.width / 640` — the scale factor
is a constant `1`, so the adjacent comment ("recorded frames might be different resolution") is
not implemented. A 1080×1920 phone clip yields coordinates far outside the canvas, and the
Motion Path panel renders empty or clipped.

**Suggested fix:** size the canvas from the recorded frames' actual coordinate extent (or from
the source frame size stored per M1) and scale by that instead of by a literal 640×480.

### M3 — Test mode uses a different rep counter than the patient session, while the UI claims they are identical

**Files:** `app/admin/exercises/[id]/edit/page.tsx:210-212` and copy at `:1061`; `app/session/page.tsx:190-192`
**Severity:** Major

The editor constructs `CycleRepCounter` (the patient must land inside the tight angle band); the
session constructs `RomCycleRepCounter` (fires at 60% of ROM travel, band never required). The
on-screen text says "This runs exactly the validation patients get". Rep counts and the
`holding`/`lowering` phase behavior therefore diverge, so tuning in the editor does not predict
session behavior.

**Suggested fix:** hoist the counter selection (and the `cyclic` predicate) into one shared
factory in `lib/poseDetection.ts` and have both call sites use it. Once done,
`CycleRepCounter` has no remaining consumer (see m20).

### M4 — `form_quality_score` counts coaching overrides as good form, and it gates level unlocks

**File:** `app/session/page.tsx:462-479` (override), `:493-496` (accumulate), `:616-618` (score); consumer `lib/levels.ts:56`
**Severity:** Major

`displayFeedback` is forced to `'good'` for the entire `lowering` phase and for `holding` once
the hold is earned. Line 493 then accumulates `goodPostureTimeRef` from that **overridden**
value, and `saveSessionToDb` turns the ratio into `form_quality_score`, which is compared
against `unlock_min_score`. The score therefore measures time spent in a phase rather than
correctness — moving slowly unlocks levels.

**Suggested fix:** accumulate good-posture time from `analysis.feedback` (the raw engine
verdict) and keep `displayFeedback` purely for the UI.

### M5 — UTC/local date mixing breaks streaks, the week strip, and "today"

**Files:** `lib/progress.ts:81,97,101,181` (UTC) vs `app/(dashboard)/page.tsx:109,163,367-369`
and `app/progress/page.tsx:50,94` (local via date-fns)
**Severity:** Major

`lib/progress.ts` derives day keys with `toISOString().split('T')[0]` (UTC); the pages derive
them with date-fns `format(d,'yyyy-MM-dd')` (local). At UTC+7 a session logged before 07:00
local falls on the previous UTC day, so:

- `computeStreak` can return 0 for a day the patient did practice.
- `weekStatsByDay.get(day.date)` misses its day, so mood faces render as rest days.
- `isToday` / `isFuture` (`app/(dashboard)/page.tsx:367-369`) ring the wrong cell near midnight.

**Suggested fix:** commit to one basis — local dates via date-fns `format` — and replace all
three `toISOString().split('T')[0]` sites in `lib/progress.ts` plus the dashboard's `today`.

### M6 — `callWorker` has no timeout; a silent worker hangs detection permanently

**Files:** `lib/poseDetection.ts:87-94`, `:136-157`; `lib/detection.worker.ts:22-42`
**Severity:** Major

`worker.onerror` fires only for uncaught **synchronous** errors. The worker's `onmessage` handler
is `async`, so a rejection inside it surfaces as `unhandledrejection` and no reply is ever
posted. The pending promise never settles → `detectInFlight` stays `true` (`:140`, `:156` never
runs) → every later `detect()` returns the stale `lastWorkerPose` forever, and `initDetector`
awaits forever. `msg.bitmap.close()` (worker `:32`) throwing is enough to trigger this.

**Suggested fix:** wrap the entire worker handler body in try/catch and always post a reply
(carrying an `error` field on failure); add a per-message timeout in `callWorker` that resolves
`null` and sets `workerBroken`.

### M7 — `exercises.recorded_paths` is multi-megabyte and downloaded by every patient session

**Files:** `app/admin/exercises/new/page.tsx:376-378,544-549`; `app/session/page.tsx:158`;
`app/admin/exercises/[id]/edit/page.tsx:294-298`
**Severity:** Major

Every captured frame is stored: up to 600 frames per demo (`MAX_FRAMES`), 2-3 demos, each frame
carrying 17 or 21 keypoints with `x`, `y`, `score`, `name`, and a `world` triple. That is on the
order of ~1 MB per body demo and several MB per exercise row. The session query selects
`recorded_paths`, and the editor selects `*` — paid on a phone, on every session start, before
the model even loads.

**Suggested fix:** down-sample before storing (`buildGuideFrames` resamples to 32 poses and DTW
resamples to 64 anyway), drop `world` for body mode where it is unused (see clarification 4),
round coordinates to whole pixels, and/or move recordings into a separate table so the session
query never pulls them.

### M8 — Async camera-setup cleanup races leave the camera on

**Files:** `app/session/page.tsx:309-356`; `app/admin/exercises/new/page.tsx:83-115`
**Severity:** Major

`stream` is assigned inside the async `setupCamera`/`startCamera` body. If the effect unmounts
before `getUserMedia` resolves (React StrictMode double-mount, fast navigation), cleanup sees
`stream === null` and never stops the tracks — the camera indicator stays lit and the
MediaStream leaks.

**Suggested fix:** track a `cancelled` flag plus a ref for the stream; in the async body, stop
the freshly acquired stream immediately if `cancelled`, and have cleanup read the ref.

### M9 — Side effects inside a `setCountdown` state updater

**File:** `app/admin/exercises/new/page.tsx:205-219`
**Severity:** Major

The updater calls `clearInterval`, `setRecordingState('recording')`, and resets
`recordedFramesRef.current` (lines 209-211). State updaters must be pure; React 19 StrictMode
invokes them twice in development, so recording can start twice or the frame buffer can be
cleared after capture has already begun.

**Suggested fix:** have the updater compute only the next countdown value, and move the
transition into the interval callback or into a `useEffect` keyed on `countdown === 0`.

### M10 — Unguarded `JSON.parse` of localStorage crashes every page that reads progress

**File:** `lib/progress.ts:70-77`; downstream `:144-164`
**Severity:** Major

A malformed `medproj_progress_<uid>` value (partial write, manual edit, another app) throws
`SyntaxError` straight to the error boundary, taking out the dashboard, the progress page, and
session completion. The spread at `:73` also guards no fields: a legacy blob missing
`totalStars`/`dailyStars` yields `undefined`, and `recordCompletion:154` then persists
`undefined + 1 = NaN`.

**Suggested fix:** try/catch around the parse, returning the default object on failure, plus
per-field coercion (`??` and `Number.isFinite`) before use.

### M11 — No rate limit on an endpoint that sends email

**File:** `app/api/notify-guardian/route.ts:21-142`
**Severity:** Major

Any signed-in patient can loop the POST and send unbounded mail to their guardian's address,
burning the shared Resend quota. The recipient is chosen server-side from the profile row, so
this is self-targeted spam rather than an open relay — still an abuse vector on a shared key.

**Suggested fix:** allow one email per `therapy_sessions.id` (tracked in a column, checked
before send), or apply a simple per-user cooldown before calling Resend.

## Needs clarification

   `lib/trajectory.ts:136-152` resamples each *entire* demo to 64 points and compares it against

   coordinates are captured and stored, but body validation stays 2D. Keep storing `world` for

5. **The `profiles` UPDATE policy lets an admin edit any other user's profile columns** except
   `is_admin` and `total_stars` — including `email` and `guardian_email`
   (`supabase/migrations/20260706000000_stars.sql:468-471`). Intended therapist capability, or

6. **Two dashboards plus a progress page:** `/` (`app/(dashboard)/page.tsx`, garden),
   `/dashboard` (`app/dashboard/page.tsx`, recharts), and `/progress` (calendar) — with

### Fix first

1. **C2** — rotate the admin password and strip it from `set-admin.sql`. Minutes of work,
   largest blast radius.
2. **C1** — the immortal detection loop. It corrupts rep counts and `form_quality_score`, leaks
   the camera and inference, and can double-complete a session. One `running` flag.
3. **C3** — revoke client writes on `therapy_sessions.stars_awarded`, `completed_at`, and
   `form_quality_score`. Without it, stars and level unlocks are self-serve and M4's gate is
   moot anyway.

Then **M1 + M2** (resolution mismatch — silently wrong validation for every uploaded demo) and
**M3** (editor test mode does not match the session).
